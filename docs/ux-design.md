# netfilterd — UI / UX design brief

This document is the complete design brief for the `netfilterd` web admin UI.
It is intentionally explicit and long: it captures the project goals, the
mental model the operator is expected to hold, the information architecture,
every page, every interaction, every popup, every empty state, and the safety
properties that shape each decision. It is written as input for a design tool
or a designer who has not seen the codebase.

---

## 1. Project context

### 1.1 What is netfilterd

`netfilterd` is a single static Go daemon that turns a Raspberry Pi 4 into a
transparent, default-deny WiFi appliance. The Pi runs a hotspot via
`hostapd`; clients connect, get DHCP from `dnsmasq`, and have their LAN
traffic forwarded through `nftables` rules generated by `netfilterd` out a
USB LTE modem (the "WAN"). A web admin UI on `https://192.168.4.1:8443` is
the operator's only surface for configuring it.

### 1.2 What it is for

The principal target is to isolate a **Tesla Model 3 / Y** from Tesla's
backend. The Tesla connects to the Pi's hotspot believing it has real
Internet, but every packet is intercepted:

- **TCP/443 (HTTPS)** for a "Filtered" device is REDIRECTed in nftables
  prerouting to a local **SNI proxy** on port 8444. The proxy reads the
  cleartext TLS SNI, checks the hostname against an allow-list, and either
  splices traffic upstream (no decryption, no MITM — TLS pinning intact) or
  drops.
- **TCP/80 (HTTP)** for a Filtered device is DNAT'd to a local "connman
  spoof" service that returns the captive-portal "you are online" response
  Tesla's `connman` expects.
- **UDP/443 (QUIC)** is dropped — clients fall back to TCP/443 through the
  SNI gate.
- **DNS** is default-deny via dnsmasq (`address=/#/` NXDOMAIN catchall),
  with per-domain `server=/<allow-listed>/upstream` overrides for what's
  allowed.
- Everything not specifically permitted is dropped at the forward chain
  (`policy drop`).

The safety stake is asymmetric: if the Tesla makes a single successful
connection to Hermes / OTA / telemetry, Tesla's fleet ops can permanently
disable the car. So the entire design language is **default-deny + explicit
operator opt-in + audit trail**. The UI is built around that discipline —
every affordance asks the operator to slow down, justify, and confirm.

### 1.3 The three pillars of the model

1. **Device "Traffic" classification** — a single column on every device
   row. Three values: `Blocked`, `Filtered`, `Open`. New devices land as
   Blocked. The operator deliberately promotes a device to Filtered or
   Open.

2. **Filters** — named, curated bundles of allow-listed domains. Each
   filter has a global on/off toggle. When a filter is ON, every domain
   it carries is allow-listed for every Filtered device on the network.
   Filters used to be per-device-attached; they are now **global** because
   in practice the operator wanted a single "YouTube" lever instead of
   attaching it to each device.

3. **The protected-deny floor** — a hardcoded, compile-time list of
   known-bad Tesla endpoints (Hermes, OTA, telemetry, manufacturing,
   engineering hosts). Consulted at three points: when adding a domain to
   a filter (rejected), when the SNI proxy decides to splice (dropped),
   when the DNS generator writes the dnsmasq config (no `server=` line).
   Deny always wins. The operator cannot override it from the UI by design.

### 1.4 Visual / interaction conventions used everywhere

- **Self-signed HTTPS** at `https://192.168.4.1:8443`. First visit shows a
  browser cert warning; the `/netfilter-ca.crt` endpoint serves the cert
  for trust installation if the operator wants a green lock.
- **Auth** via a single `admin` user. Username + password set during
  first-boot provisioning. Auth cookie persists; `AuthRequired` middleware
  gates every page route. API uses the same session cookie
  (`APIAuthRequired`).
- **Framework**: server-rendered HTML via Go `html/template`, with
  **Alpine.js** for reactivity (each page is one `x-data="…App()"` root)
  and **Pico.css** for base styling. Embedded into the binary via
  `embed.FS`.
- **Notifications**: a single global toast system
  (`notify(msg, 'success'|'error')`). Used for every state-changing
  action — success in green, error in red. Errors from API calls
  auto-toast via a shared `api.request` wrapper, so handlers usually just
  call `api.post(...)` inside a `try { ... } catch(e) {}` and rely on the
  wrapper to surface the message.
- **Status colors** — a consistent palette across every page:
  - `Blocked` → red (`var(--danger)`)
  - `Filtered` → brand primary blue (`var(--primary)`)
  - `Open` → green (`var(--ins-color)`)
  - Off / inert / "Pending" → muted grey (`var(--text-muted)`)
  - "Allowed" or "applied" → green success badge
- **Toggles** — a custom CSS `.toggle` class wrapping a real
  `<input type="checkbox">` so accessibility (label clicks, keyboard) works.
  Always bound via `x-model` + `@change` (NOT `:checked` + click-prevent —
  that pattern had a bug where the visible state didn't sync with the data).
- **Tables** — Pico's base `<table>` with a thin row separator. Action
  cells right-aligned. Status badges left-aligned at the start of a row.
- **Forms** — labels above inputs, helper text in muted-color `<small>`
  directly under the input. Submit on Enter where natural.
- **Dialogs** — native `<dialog>` element opened with `showModal()`. Header
  row has a title on the left and a non-button-style `✕` close icon on the
  right (the "esc-equivalent" affordance). Body has explanatory text first,
  then form. Footer row right-aligned with Cancel on the left and the
  primary action on the right.

## 2. Information architecture

### 2.1 Top-level nav (left sidebar, persistent on every authenticated page)

In this order, each item is an icon + label:

1. **Dashboard** (`/`) — landing page, summary stats
2. **Devices** (`/devices`) — every device the Pi has seen, with its
   Traffic classification
3. **Traffic** (`/traffic`) — live traffic monitor (DNS + forward events)
4. **Stats** (`/stats`) — aggregations: top domains, top clients,
   time series
5. **Firewall** (`/firewall`) — manual nftables rules (raw escape hatch)
6. **Filters** (`/filters`) — the curated domain bundles
7. **Bandwidth** (`/bandwidth`) — per-MAC rate limits
8. **Settings** (`/settings`) — hotspot SSID/password, admin password,
   DNS upstream

The currently-active item gets a filled background. Hovering an inactive
item gives a subtle highlight.

### 2.2 Why two separate traffic-related pages?

- **Traffic** is *raw event stream* — every DNS query and every forward
  verdict, paginated, filterable, real-time-tailing. The operator scrolls
  it during testing to confirm specific behavior (e.g. "did the Tesla try
  Hermes?").
- **Stats** is *aggregations over time* — top 10 domains by hits, top 10
  clients by volume, requests-per-minute time series. The operator opens
  this to spot anomalies or noisy clients.

They're separate because the questions they answer differ: Traffic answers
"did X happen?", Stats answers "what's normal?".

## 3. Page-by-page detail

### 3.1 `/login` (public)

**Purpose**: get an unauthenticated visitor into the admin UI.

**Layout**: centered single-column card on a plain background. Title
"NetFilter — sign in". Two inputs (username, password). One submit button
"Sign in". No "forgot password" link — the admin password is reset via the
binary's CLI flag or the Settings page once logged in.

**Behavior**:

- POST `/api/login` with `{username, password}`. On success, the server
  sets a session cookie and the page redirects to `/`. On failure, an
  inline error appears under the form ("Invalid credentials"). No rate
  limiting in the UI; backend logs failed attempts to audit.
- If a user hits any authenticated route without a session, they're
  redirected here. The original URL is *not* preserved across the
  redirect (room for improvement).

**Notes**: This is the only page that does NOT show the side nav.

### 3.2 `/` — Dashboard (auth)

**Purpose**: at-a-glance health of the appliance. Fast scan, no actions.

**Layout**: a 4-up grid of stat cards (the top row), then a 4-up grid of
system info cards (the bottom row).

**Top row (operational stats)**:

| Card | Value | Subtext |
|---|---|---|
| Devices Online | `X / Y` (online over total seen ever) | "online / total" |
| Firewall Rules | count of enabled rules from the `/firewall` page | "active rules (default: deny all)" |
| Filters | `enabled / total` | "enabled / total" |
| Uptime | formatted system uptime | system load average |

**Bottom row (network info)**:

| Card | Value | Subtext |
|---|---|---|
| WAN Interface | `usb0` / `eth1` (whatever auto-detected) | `IP: <wan-ip>` |
| WAN Traffic | bytes received | bytes transmitted |
| LAN Interface | `wlan0` | hotspot SSID (e.g. `ivanchokara🌶️`) |
| LAN Traffic | bytes received from clients | bytes transmitted to clients |

**Auto-refresh**: polls `/api/dashboard` every 5 seconds. No spinners —
values update in place.

**No actions on this page.** It's a glanceable read-only board.

**Known UX gap**: doesn't surface "WAN unreachable" prominently. If the LTE
modem dies, the operator currently has to notice that nothing resolves.
Logged for future iteration: add a "WAN reachable: yes/no" indicator that
performs a small TCP-connect probe to e.g. 1.1.1.1:53 every minute.

### 3.3 `/devices` — Devices (auth)

**Purpose**: the operator's primary control surface. Every device the Pi
has ever leased an IP to or seen via ARP appears here. The operator's job
is to classify each one (`Blocked` / `Filtered` / `Open`), name
unrecognised devices with an alias, and delete devices that shouldn't
have been here.

**Header**: one line of text — "X online / Y total — new devices land as
**Blocked**. Promote to **Filtered** (SNI-gated by enabled filters) or
**Open** (full passthrough)." Plus a "Refresh" button on the right that
re-fetches without auto-polling (this page does not live-tail).

**Table columns**:

1. **Online** — green "Online" badge or muted "Offline" badge based on
   last-seen within 5 minutes.
2. **Name** — alias if set, else hostname from DHCP, else "Unknown". If
   both alias and hostname exist, hostname appears in muted small text
   beneath the alias.
3. **MAC** — monospace small text.
4. **IP** — last-known DHCP-leased address, or `-`.
5. **Traffic** — *the* primary control. A `<select>` dropdown with three
   options: Blocked / Filtered / Open. The dropdown border and text color
   match the status: red border for Blocked, blue for Filtered, green for
   Open. Visual state IS the value.
6. **Log** — a toggle. ON = events from this device are written to
   `query_log`. OFF = events from this device are dropped before they're
   written (firewall rules still apply; only the audit/log is suppressed).
7. **Edit** — a row of buttons:
   - `Edit` (outline button) — opens the edit dialog
   - `×` (red outline button) — delete the device

**Row interactions**:

- **Traffic dropdown change** → optimistic UI update + PUT
  `/api/devices/{mac}/status` with `{status: "filtered"}`. On success:
  toast "`<alias|mac>` → filtered". On failure: dropdown reverts to
  previous value, error toast surfaces from the API wrapper.
  - Behind the scenes the handler ALSO calls `firewall.Apply()` and
    `dns.Apply()` so the change is live by the time the toast shows.
  - Status colors update on the dropdown itself the moment the user
    releases the mouse.

- **Log toggle off** → confirmation dialog: "Stop logging traffic from
  `<name>` and wipe its existing history from the traffic monitor?
  Firewall rules will continue to apply unchanged." Confirming triggers
  PUT `/api/devices/{mac}` with `{alias, ignore_traffic_log: true}` AND
  deletes existing rows for this MAC's events from `query_log` (forward
  events matched by MAC, DNS events matched by client IP).

- **Log toggle on** → no confirmation. Just a PUT with
  `ignore_traffic_log: false`. Future events will be logged again;
  previously-wiped rows are gone for good.

- **`Edit` button** → opens the **Edit Device dialog**:
  - Title: "Edit Device". No close X (just Cancel button) — this is a
    pre-existing dialog that hasn't been updated to the new convention;
    should be unified in a polish pass.
  - Fields:
    - `Alias` text input — operator-friendly name. The alias overrides
      the DHCP hostname in displays.
    - `Ignore traffic logs` checkbox with helper text: "Drops events from
      the traffic monitor before insert (firewall rules unaffected).
      Enabling wipes existing history for this device."
  - Footer: `Cancel` (outline secondary) + `Save` (primary). Save → PUT
    `/api/devices/{mac}`, then toast "Device updated", then refresh.

- **`×` delete button** → `confirm("Forget device \"<name>\"?\n\nIts
  traffic-log history is wiped. If it reconnects it lands as Blocked.")`.
  Confirming → DELETE `/api/devices/{mac}`. The handler:
  1. Snapshots the IP before deletion (for log-wipe by client_ip on
     DNS events)
  2. Removes the row from `devices`
  3. Wipes the device's `query_log` history
  4. Re-applies firewall + DNS
  5. If the device reconnects later, the network scanner's `upsertDevice`
     re-inserts it with `status='blocked'` (explicit in the INSERT, not
     relying on column default) — so it lands as Blocked, indistinguishable
     from a first-time-seen device.

**Empty state**: if no devices have been seen, the table is empty. There's
no explicit empty-state illustration here; the "online / total" line just
says "0 online / 0 total".

**What was removed in the recent UX refactor**:

- A "Presets" column that showed which presets were attached to this
  device, with a `+ add preset...` micro-dropdown. Removed because
  filters became global.
- A `Blocked` toggle column. Replaced by the unified Traffic dropdown —
  Blocked is just a status value now.

### 3.4 `/filters` — Filters (auth)

**Purpose**: maintain the global allow-list bundles. Each filter is a
named list of domains; flipping a filter on means every domain inside it
(whose individual `enabled` flag is also on) becomes resolvable and
SNI-spliceable for every Filtered device on the network.

**Header**: title "Filters" + helper text — "Each filter is a curated
list of allow-listed domains. Toggle a filter on to apply it to **every**
Filtered device. System filters ship with the binary and cannot be
deleted (you can still edit their domain list)." + a "+ New filter"
button on the right.

**The "+ New filter" form** appears in-place below the header when toggled.
Inline form:

- `Name` text input — validated as 1–64 chars matching
  `^[A-Za-z0-9][A-Za-z0-9 _+/-]{0,63}$`. The `+` and `/` are allowed so
  "Disney+" and "Tesla AP/Nav" are spellable.
- `Description` textarea (2 rows) — REQUIRED. The submit handler rejects
  if `description.trim() === ''` with a toast "Description required —
  explain what this filter unlocks".
- `Save` button → POST `/api/filters` with `{name, description}`. New
  filters start OFF and empty.

**Filter list**: each filter is an `<article>` card.

**Card header (collapsed state)**:

- Left side:
  - Filter name in bold.
  - `system` badge (small, brand-primary background) if `is_system=true`.
  - Status badge — green "applied to all Filtered devices" if enabled,
    muted "off — not applied" if disabled.
  - Description in muted small text on the second line.
- Right side (three controls in a row):
  - **The big enable toggle** — a standard `.toggle`. Flipping it calls
    PUT `/api/filters/{id}/enabled` with `{enabled: bool}` and DNS-applies.
    Tooltip explains the consequence: "Click to turn this filter on — its
    domains apply to every Filtered device".
  - `Edit` / `Hide` button — expands the card.
  - `Delete` button — only shown if `!is_system`. Confirms first: "Delete
    filter \"X\"? Filtered devices lose every domain it carried." Then
    DELETE `/api/filters/{id}` + DNS apply.

**Card expanded body** (when Edit clicked):

- Helper text at top: "Every entry needs a **description** — justify why
  the domain is on the list so the audit trail tells a story."
- An add-domain row (three columns: domain input, description input, Add
  button). Both inputs accept Enter to submit.
  - On Add: validates locally that description is non-empty (toast
    "Description required — justify every allow-list entry" if not), then
    POST `/api/filters/{id}/domains` with `{domain, description}`.
    Server-side, `CreateDomain` runs three additional checks:
    1. **Normalize**: lowercases, strips leading `*.`, validates against
       the strict domain regex.
    2. **Protected-deny floor**: if the domain is on the hardcoded
       `protectedDeny` list (Hermes/OTA/telemetry/etc.), reject with
       `"\"X\" is a protected Tesla endpoint and cannot be allow-listed"`.
    3. **Protected-ancestor check**: if the domain is a broader parent of
       any protectedDeny entry (e.g. `tesla.services` would re-admit
       Hermes via suffix matching), reject with `"\"X\" is too broad — it
       would admit a protected Tesla endpoint; allow the specific
       sub-domain instead"`.
  - On success: toast "Added (disabled — review and toggle on)". The new
    domain row appears in the table below, with its `On` toggle OFF. This
    is the **review-then-enable safety pattern** — even though the
    operator just typed the domain, they have to take one more deliberate
    action (the per-domain toggle) before it goes live. This protects
    against typo-driven additions.

- A small helper line: "New domains are added **disabled**. Toggle each
  on after reviewing."

- **Domains table** with columns:
  - `On` (60px) — a toggle. Flipping calls PUT
    `/api/filters/domains/{id}/enabled` with `{enabled: bool}` + DNS
    apply. The description is NOT re-sent (the toggle endpoint is
    separate from the update endpoint because the original add-time
    description should remain authoritative).
  - `Domain (SNI suffix)` — monospaced; the literal hostname.
  - `Why` — the description in muted small text. Should always be present
    (it's required at insert).
  - actions (90px) — `×` button to delete the domain.

**Domain delete flow**: `confirm("Remove <domain> from <filter>?")` then
DELETE `/api/filters/domains/{id}` + DNS apply.

**Empty domains state**: "No domains yet. Add one above." in muted text.

**The four system filters that ship out of the box** (seeded by migration
v15, renamed in v16):

1. **Tesla AP/Nav** — `daws.tesla.services`, `apmv3.go.tesla.services`,
   `maps-eu-prd.go.tesla.services`, `maps.googleapis.com`. Curated to be
   nav-only — explicitly NOT including `auth.tesla.com` (Akamai cert
   overlap with `toolbox`/`epc`), bare `go.tesla.services` (suffix would
   re-admit `navsrv.eng.go.tesla.services`), or
   `managed-charging.sn.tesla.services`. This is the audit floor for what's
   safe to allow on the Tesla.
2. **YouTube** — `youtube.com`, `googlevideo.com`, `ytimg.com`,
   `ggpht.com`, `youtu.be`.
3. **Netflix** — `netflix.com`, `nflxvideo.net`, `nflximg.com`,
   `nflxext.com`, `nflxso.net`.
4. **Disney+** — `disneyplus.com`, `disney-plus.net`, `dssott.com`,
   `bamgrid.com`.

System filters can be edited (add more domains, toggle individual ones)
but not deleted. The Delete button doesn't render for them.

### 3.5 `/traffic` — Traffic monitor (auth)

**Purpose**: live view of every DNS query and every forward verdict. The
operator uses this for debugging ("did the Tesla try X?") and confirmation
testing.

**Layout**: a header bar with controls, then a wide table, then pagination.

**Header bar (left to right)**:

- **Live / Paused** badge — green "Live" or muted "Paused". Click to
  toggle.
- A "Pause" / "Resume" button. When live, page 1 auto-refreshes every 3
  seconds. Pausing stops the timer and freezes the view; pagination still
  works.
- Source filter chips: "All", "DNS", "Forward". Clicking one filters by
  `source`.
- Action filter dropdown: `<select>` over the action enum (`query`,
  `allowed`, `blocked`, `logged`).
- Free-text search input (FTS over domain, client IP, dst IP, dst port).
  Submits on Enter or after 300ms debounce.
- Date range: two `datetime-local` inputs for from/to. Applied immediately.
- A "Muted (N)" button (right-aligned) — N is the count of muted-domain
  patterns. Click → opens the **Muted domains dialog** (described below).

**Table columns**:

1. `Time` — `HH:MM:SS` (or full ISO in tooltip).
2. `Source` — small badge: `dns` or `forward`.
3. `Client` — IP (small monospace). Tooltip shows alias/hostname if known.
4. `Domain` — the queried/looked-up hostname. If unknown, the column
   shows `-`. When dst_ip is meaningful, it appears in muted small text
   on a second line.
5. `Port` — destination port.
6. `Proto` — TCP / UDP / DNS / TLS / QUERY.
7. `Action` — colored badge:
   - `allowed` → green
   - `blocked` → red
   - `query` → blue (info)
   - `logged` → muted
8. `Actions` — cell with up to two controls (described below).

**The Actions cell** (per row):

This is the meaningful interaction column. The state and what's shown
depends on the relationship between the event's domain and the current
filter context (which is loaded once on page load via
`loadFilterContext()`):

- If the event's source device is **Open**: badge "✓ Open" (green).
  Tooltip: "Open device — no SNI gate". No Allow button — there's
  nothing to allow, the device already has full passthrough.
- If the domain is in a live allow-list (a domain that's enabled AND
  inside a filter that's enabled): badge "✓ Allowed" (green). Tooltip:
  "Resolved through an enabled filter".
- If the domain is in a filter but the filter or the domain is disabled:
  badge "Pending" (muted). Tooltip: "Staged in a filter but disabled —
  toggle it on under /filters".
- Otherwise (the domain isn't in any filter at all): **Allow button**
  (small outline). Click → opens the **Allow → pick filter dialog**
  (described below).

Plus, always on a row with a domain: a separate **Mute** button (small,
muted text). Click → POST `/api/system/traffic/muted` with `{domain}`.
Behind the scenes the backend always stores mutes as suffix-match, so
muting `apple.com` swallows every `*.apple.com` event in one row. Toast:
"Muted X — new events will be dropped".

#### 3.5.1 The Allow → pick filter dialog (the key new flow)

This is the popup that surfaces when the operator hits "Allow" on a
traffic row. It captures the operator's intent in one place:

**Title**: "Allow `<domain>`" — the domain inline as code.

**Top-right**: `✕` close icon (consistent with the muted dialog).

**Body explanation** (muted helper text at the top of the dialog):

> Pick the filter list this domain belongs in. Filters apply **globally**
> to every Filtered device, so put domains under the service they serve
> (YouTube hosts under YouTube, Tesla nav under Tesla AP/Nav, etc.). A
> description is required — explain *why* this domain is on the list.

**Body controls**:

1. **Filter list** — `<select>` dropdown.
   - Each existing filter shows as `<name> (on)` or `<name> (off)`,
     indicating its current global state.
   - Last option: `＋ Create a new filter list…` (with a leading plus
     glyph).
2. **Inline "create new filter" mini-form**, visible (`x-show`) only when
   the operator selects the `+ Create` option:
   - Boxed area with a dashed border and muted background to make it
     visually distinct.
   - `Filter list name` text input.
   - `Description` textarea.
   - Helper text: "The new filter starts **off** — flip it on under
     /filters once you've reviewed its contents." (This is intentional:
     even when the operator creates a new filter from this fast path,
     they still have to come back to /filters and flip the global enable.
     Two-step.)
3. **Why this domain?** — text input. Required. Label says "Why this
   domain?" with placeholder example "e.g. Netflix video CDN — required
   for playback".

**Body bottom helper text**:

> The domain is added **disabled**. Flip it on under /filters after a
> final read-over.

**Footer**:

- `Cancel` (outline secondary).
- `Add to filter` (primary) — disabled until BOTH the description is
  non-empty AND a filter is selected (or the new-filter form is complete).

**Submit flow** (`submitAllow`):

1. Validate the description is non-empty client-side. If empty, toast
   "Description required — justify the allow-list entry" and stop.
2. If the operator selected "Create new":
   - Validate `newFilterForm.name` and `newFilterForm.description` are
     non-empty (toast on failure).
   - POST `/api/filters` with `{name, description}`. The new filter is
     created with `enabled=0`.
   - Capture the returned `id` as the target.
3. POST `/api/filters/{filterID}/domains` with `{domain, description}`.
   The server runs the same `CreateDomain` validations (NormalizeDomain
   → ErrDescRequired check → protected-deny → protected-ancestor →
   upsert with `enabled=0`).
4. Toast: "Added `<domain>` (disabled — review and toggle on under
   /filters)".
5. Close the dialog.
6. Re-load the filter context (`loadFilterContext()`) so the row in the
   traffic monitor updates from "Allow" button to "Pending" badge
   in-place.
7. Reload the current page of traffic events (`load()`) so the user sees
   the live row update.

**Why three layers of friction** (pick filter → write description →
still disabled after add): the cost of accidentally allow-listing a wrong
domain is asymmetric. A typo here, in the heat of debugging, can re-admit
a protected Tesla endpoint that the protected-deny floor doesn't catch
(e.g. some legitimately-named CDN that happens to share infrastructure).
The friction is the safety.

#### 3.5.2 The Muted dialog

Opened from the "Muted (N)" button.

**Title**: "Muted domains".

**Top-right**: `✕` close button.

**Body explainer** (muted small text):

> Events for these domains are dropped before they reach the monitor
> (firewall rules are unaffected). A pattern is treated as a **suffix
> match**: muting `apple.com` swallows every `*.apple.com` sub-host in
> one row.

**Add row** (always at the top of the body):

- Text input with placeholder "domain or suffix (e.g. apple.com)".
- `Mute` button. Disabled while the input is empty.
- Enter in the input submits.

**Submit** → POST `/api/system/traffic/muted` with `{domain}`. Toast:
"Muted `<x>` (and every *.`<x>`)". The list re-loads.

**Existing mutes table**:

- `Pattern` column: the literal pattern, monospaced, with the
  `match_type` (always "suffix" in practice) in muted small text next
  to it.
- Action: `✕` button to unmute. Confirms via the API (DELETE
  `/api/system/traffic/muted/{id}`).

**Empty state**: "Nothing muted yet — add a suffix above or use the
**Mute** button on a noisy row."

### 3.6 `/stats` — Stats (auth)

**Purpose**: aggregated view to spot anomalies and noisy devices.

**Layout**: three sections vertically:

1. **Top domains** — table of the top 10 most-queried domains in the
   last 24 hours, with hit counts.
2. **Top clients** — table of the top 10 most-active client IPs by
   request volume.
3. **Time series** — a line chart (Chart.js) of requests per minute
   over the last hour, with separate lines for `query`, `allowed`, and
   `blocked`.

**Top domains table columns**:

- Domain
- Hits (number, with thousand separators)
- Action: `Allow` button (quick allow — needs to go through the same
  Allow → pick filter dialog as /traffic, *but currently does not*; this
  is a known gap from the recent refactor). The button currently
  triggers a simplified path that posts to `/api/firewall/rules` —
  that's a pre-existing flow from V2 that should be rewritten to open
  the modal.

**Top clients table columns**:

- Client IP
- Hits
- Action: `Block` button (which currently mutes the domain via
  `/api/system/traffic/muted`; it used to add to the dns_blocklist which
  no longer exists).

**Chart**: dark mode, three series, X-axis is time, Y-axis is request
count. Tooltips on hover.

**Known UX gap**: the Allow/Block buttons on this page are vestigial —
they predate the filter model and the muted-dialog rework. They should
be aligned with the /traffic Actions cell semantics in a polish pass.

### 3.7 `/firewall` — Firewall (auth)

**Purpose**: raw nftables-style rule entry as an escape hatch. Most
operators never touch this; it exists so you can express something the
Filter / Devices model can't.

**Layout**: a list of rule rows + an "Add rule" button at the top.

**Each rule row** shows: direction (inbound/outbound/forward), protocol
(tcp/udp/icmp/all), source IP, dest IP, dest port, action
(drop/reject/accept), device MAC (optional), enabled toggle, priority.
The fields map 1:1 to the `firewall_rules` table.

**Add/edit form** is a wide dialog. No client-side validation beyond
"fields present" — the backend rejects malformed values.

**Why this exists alongside Filters**: Filters operate at the SNI/DNS
layer. Firewall rules operate at the nftables layer (L3/L4). Both can
co-exist. In practice the Filter model is what the operator uses 99% of
the time; this page is the "I need to drop all UDP from this MAC for an
hour" kind of thing.

### 3.8 `/bandwidth` — Bandwidth (auth)

**Purpose**: per-MAC ingress/egress rate limits via `tc`.

**Layout**: simple table — MAC, alias (joined from devices), download
Kbps, upload Kbps, enabled toggle, edit/delete actions.

**Add form**: MAC dropdown (populated from devices), two number inputs
for the rate limits, an enabled checkbox.

**Limits are enforced** by `BandwidthService.Apply()` shelling out to
`tc` on the configured LAN interface. The UI is just a CRUD wrapper.

### 3.9 `/settings` — Settings (auth)

**Purpose**: appliance-level configuration that isn't device- or
filter-scoped.

**Sections**:

1. **Admin password change** — current password, new password, confirm.
   Submit → PUT `/api/settings/password`. Logs the user out on success.
2. **Hotspot settings** — SSID, hotspot password. Submit → PUT
   `/api/settings`. Behind the scenes, `HotspotService.Apply()`
   regenerates `/etc/hostapd/hostapd.conf` and restarts hostapd.
3. **DNS upstream** — comma-separated list of public resolvers. Default
   `1.1.1.1,8.8.8.8`. Used by dnsmasq for the
   `server=/<allowed>/<upstream>` lines and by the Open-device DNS DNAT
   rule.

Each section has its own `Save` button; saves are scoped.

**Friction**: changing the hotspot SSID/password kicks every client off
until they reconnect. There's a confirmation dialog ("Connected clients
will be disconnected. Continue?") before applying.

## 4. Cross-cutting flows + states

### 4.1 Authentication flow

1. Pi boots. First-boot provisioning runs `setup.sh`, which reads
   `answers.txt` from the SD card and creates the admin user with the
   supplied password.
2. Operator visits `https://192.168.4.1:8443`. Browser shows cert
   warning (self-signed). They click through.
3. Redirected to `/login`. Submit credentials.
4. On success, session cookie (`netfilter_session`) is set with
   `HttpOnly + Secure + SameSite=Lax`. Redirect to `/`.
5. Every API call sends the cookie. Backend looks up the session; if
   expired or missing, returns 401, the API wrapper auto-redirects to
   `/login`.
6. Logout button (top right of the layout — actually currently in the
   side nav footer; should be more discoverable) → POST `/api/logout`
   → cookie cleared → redirect to `/login`.

### 4.2 Notification (toast) system

Single global `notify(msg, kind)` function shared across all pages.
Renders a brief slide-in toast at the bottom-right of the viewport.
Auto-dismisses after 4 seconds; clicking dismisses immediately. Kinds:

- `success` → green
- `error` → red
- `info` → blue (rarely used)

The `api.request` wrapper auto-toasts errors from non-2xx responses with
the server's error message in the body. So most handlers
`try { await api.post(...); notify('thing happened', 'success') } catch(e) {}`
and the error path is implicit.

### 4.3 Confirmation pattern

Native `window.confirm()` is used for destructive but reversible actions
(delete filter, delete device, unmute a domain). For more nuanced
confirmations (the log-toggle wipe), the confirm text spells out the
consequence explicitly: "Stop logging traffic from ... and wipe its
existing history".

For non-destructive but irreversible safety actions (Allow → pick
filter), the friction is the popup itself + the disabled-by-default
landing — there's no `confirm()` because the popup IS the confirmation.

### 4.4 Empty states

Every list view has a muted, centered "nothing yet" line that tells the
operator what to do next:

- Devices: implicit — empty table just shows "0 online / 0 total".
- Filters domain list: "No domains yet. Add one above."
- Muted domains: "Nothing muted yet — add a suffix above or use the
  **Mute** button on a noisy row."
- Top domains / clients: "No activity yet."

### 4.5 Live-tail behavior

Only `/traffic` live-tails (3-second polling on page 1 when not paused,
no date filter active, and no manual pagination). All other pages are
operator-pull (manual refresh button or page-load only).

### 4.6 Color semantics recap (consistency check)

| Semantic | Color | Use sites |
|---|---|---|
| **Blocked / danger / drop** | Red `var(--danger)` | Devices Traffic dropdown for Blocked; firewall drop action; delete buttons |
| **Filtered / primary / brand** | Blue `var(--primary)` | Devices Traffic dropdown for Filtered; the active nav item highlight |
| **Open / passthrough / success** | Green `var(--ins-color)` | Devices Traffic dropdown for Open; Online badges; "✓ Allowed" badges |
| **Off / inert / muted info** | Grey `var(--text-muted)` | Disabled toggles; "Pending" badges; helper text; system badges |
| **System-curated** | Brand-primary mini-badge | The "system" tag next to Tesla AP/Nav, YouTube, etc. |

### 4.7 Safety properties surfaced in UX

The whole design is shaped by the asymmetric Tesla-ban risk. Specific
places where that shows up:

1. **Default = Blocked**. A device the operator hasn't seen before
   contributes zero allow. The UI labels it Blocked the moment it
   appears.
2. **Two toggles for every domain to be live**: per-domain `enabled`
   flag PLUS per-filter `enabled` flag. The operator can't have a domain
   "accidentally on" without flipping two intentional switches.
3. **Description required** on every domain add. The act of typing a
   justification is friction that prevents reflex-typed allow-lists.
4. **Protected-deny floor surfaces as inline errors** in the Allow
   dialog and the add-domain form. If the operator types
   `hermes-prd.ap.tesla.services`, the toast tells them exactly why it
   was rejected and points them at the safe alternative.
5. **System filters are non-deletable**. The audited Tesla AP/Nav set
   can be added to (with friction) but never accidentally removed.
6. **"Open" is a clearly-marked third state**, not the default. Its
   color (green) and the explanatory text on /devices ("no SNI gate")
   make the operator aware they're handing a device full passthrough.
7. **Delete a device → it returns as Blocked**, never as the previous
   status. The UX message on the delete confirm makes that explicit.

## 5. What's intentionally NOT in the UI

These are decisions to *not* surface things, made for safety or clarity:

- **No UI for editing the protected-deny floor**. It's compile-time
  code. The operator cannot override it from the UI.
- **No "allow everything for one minute" debug mode**. There's no fast
  escape hatch; debugging requires deliberate filter edits.
- **No bulk "mark all Online devices as Open"**. Bulk operations are
  easy to misuse.
- **No "import filter from URL"**. Trust boundary; would let a remote
  bad actor sneak a Hermes domain into a filter via a poisoned share
  link.
- **No password recovery flow from `/login`**. Recovery is via CLI on
  the Pi.

## 6. Mental model the operator needs

A device is one of three things; filters are global on/off lists of
explicitly-justified domains; the system says no by default and asks you
to justify every yes. Everything else is implementation detail behind
that.
